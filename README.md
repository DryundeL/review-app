# Review App (frontend)

Telegram Mini App клиент на React. Go API — отдельный репозиторий.

## Стек

React 19 · TypeScript · Vite · React Router · TanStack Query · Zustand · React Hook Form + Zod · Tiptap · Radix UI

## Архитектура (FSD)

```
app → pages → widgets → features → entities → shared
```

Telegram SDK изолирован в `shared/platform` (адаптеры `telegram` / `web`).

## Запуск

```bash
npm install
cp .env.example .env
npm run dev
```

`VITE_API_BASE_URL` указывает браузеру на Go API. `SSR_API_BASE_URL` — отдельный
фиксированный URL API для Node.js (например, `http://127.0.0.1:8080`). Он
используется только сервером и не зависит от входящих Host/cookies/Authorization.
`npm run dev` запускает SSR-сервер с Vite middleware и HMR.

`npm run build` создаёт `dist/client` и `dist/server`.
`npm start` запускает production SSR на `0.0.0.0:8080`; адрес и порт меняются
через `HOST` и `PORT`. После сборки: `npm run test:ssr` проверяет HTML, метаданные,
HTTP-статусы, изоляцию запросов и защиту данных. `npm test` запускает unit-тесты.

## Страница произведения и приватность

`/media-objects/:mediaId` открывается из поиска и страницы обзора. Информация
загружается через `GET /v1/media-objects/:id`, топ-5 — отдельным запросом
`GET /v1/media-objects/:id/top-reviews`. Метаданные каталога читаются из `info`.
Порядок обзоров определяет API; клиент проверяет размер списка и статус публикации.

В `/settings` доступен переключатель `isProfilePrivate`. У владельца приватного
профиля третья вкладка «Запросы» содержит входящие запросы на подписку
с принятием, отклонением и загрузкой следующих страниц. Кнопки подписки
различают `none`, `pending` и `following`; запрос не увеличивает счётчики подписок.
Уведомление `follow_request` ведёт в `/profile?tab=requests`.

Каталог, поиск, опубликованные обзоры и публичные профили доступны гостям.
Изменения, личные разделы и настройки требуют входа. Недоступный приватный
профиль отображается без его содержимого; подписка доступна через отдельный статус.
Контракты backend описаны в [frontend-api-changes.md](frontend-api-changes.md).

## Форматирование обзоров

Редактор Tiptap сохраняет `blocks[].body` как HTML: абзацы, переносы, жирный,
курсив, зачёркивание, списки и спойлеры (`span[data-spoiler="true"]`).
DOMPurify очищает HTML при вставке, загрузке в редактор, отправке и отображении;
просмотр создаёт React-элементы без переноса произвольных атрибутов.
Старый текст и спойлеры `||текст||` поддерживаются.

При создании и обновлении текст каждого `body` ограничен 500 Unicode-кодовыми точками.
HTML-теги и атрибуты не учитываются; HTML-сущности декодируются перед подсчётом. Превышение отклоняется без обрезания текста. Заголовок
блока ограничен 50 кодовыми точками. Ответы API могут содержать более длинный `body`.
Сервер обязан независимо проверять запись (HTTP 422 `VALIDATION_ERROR`,
`details.field = "blocks"`) и очищать HTML: клиентскую проверку можно обойти.
В домене и БД лимита `body` нет; миграция `00024_review_block_body_length.sql`
относится к отдельному репозиторию Go API.
## Серверный рендеринг

SSR включён для `/`, `/search` (включая `?q=` и `?tab=`),
`/media-objects/:id`, `/reviews/:id` и `/profiles/:id`. Ответ сразу содержит
содержимое, title, description, canonical и Open Graph; после загрузки JavaScript
React гидратирует его с данными TanStack Query без повторной загрузки страницы.
На каждый HTTP-запрос создаётся отдельный QueryClient; пользовательская сессия
остаётся в браузере. Сохранённые фильтры ленты восстанавливаются после гидратации.

SSR работает только с гостевыми данными. Черновики, закрытые профили и неизвестные
объекты возвращают 404 без содержимого. Личные маршруты остаются клиентскими
и получают `noindex`. Недоступность основного API возвращает 503 с `Retry-After`,
а не пустой успешный ответ; таймаут загрузки данных — 5 секунд.
HTML не кэшируется. Внешние данные экранируются и в метатегах, и в JSON гидратации.

Реализация следует [Vite SSR](https://vite.dev/guide/ssr),
[React hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot)
и [TanStack Query SSR](https://tanstack.com/query/latest/docs/framework/react/guides/ssr).

## Sitemap

`/sitemap.xml` — динамический sitemap index. В нём перечислены
`/sitemap-pages.xml` (главная), `/sitemap-media-objects-N.xml`,
`/sitemap-reviews-N.xml` и `/sitemap-authors-N.xml`. Все XML-файлы расположены
в корне сайта, ссылки строятся из ID на фиксированном canonical-домене.

Node.js обходит `GET /v1/sitemap/:entity?limit=1000&cursor=...` до пустого
`nextCursor`. В карты попадают все произведения, опубликованные обзоры и публичные
профили, включая пользователей без обзоров. Опубликованные обзоры приватных авторов
остаются в sitemap; закрытые профили и черновики исключает backend.
`lastmod` не добавляется, поскольку API не возвращает достоверной даты изменения.

XML разбивается по 50 000 URL с проверкой ограничения 50 МБ на файл.
Готовый набор хранится в памяти процесса 5 минут и пересобирается при следующем
обращении. Параллельные запросы используют одну генерацию; набор заменяется только
после полного успешного обхода трёх сущностей. Ответы имеют `Cache-Control: no-store`.
При ошибке API просроченный или частичный sitemap не выдаётся: ответ 503 и
`Retry-After: 30`. Если большой обход не завершился за 20 секунд, он продолжается
в фоне, а текущий HTTP-запрос также получает 503. Ошибка генерации ограничивает
следующую попытку паузой 30 секунд. При перезапуске процесса кэш пересобирается.

Контракт описан в [frontend-api-changes.md](frontend-api-changes.md).
Правила разбиения — [Sitemaps protocol](https://www.sitemaps.org/protocol.html).
